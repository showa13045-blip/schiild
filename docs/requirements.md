### 0.3 v0.4の変更: ギルドの廃止

ギルドはデータモデルとキャッシュポイントに存在しながら、画面仕様にもユーザー体験にも一度も登場しない孤児概念であった。**廃止し、公式アトリエのみで成立させる。**

| 項目 | 変更 |
|---|---|
| `guilds` テーブル | 削除 |
| `ateliers.guild_id` | 削除 |
| S-08 ギルド管理画面 | **公式アトリエ管理画面**へ置換（1クリエイターが自分のアトリエを管理する） |
| 公式ギルド作成費用 / 大人数ギルド作成費用 | **公式アトリエ作成費用（定員帯による価格差あり）**へ置換 |
| KPI「公式ギルド数」 | 「公式アトリエ数」へ置換 |
| 複数アトリエの束ね | **束ねない。** 各アトリエは完全に独立する |

**廃止できる理由**: ギルドが解いていたのは「定員上限を超えるファンをどう収容するか」という問題である。公式アトリエのキャンバスを拡大して定員を緩和すれば、推しは1つのアトリエで足りるため、束ねる器そのものが不要になる（§4.8）。

### 0.4 v0.5の変更: 構図モデルと美的要件の再定義

#### (1) Hilbert分割 → 矩形分割（BSP）

シールトの内部を、Hilbert曲線による有機的な領域ではなく、**大きさが不揃いの矩形タイル**で敷き詰める。分割は再帰的二分割（BSP）で行い、日ごとのシードで構図が変わる。

| 項目 | 変更 |
|---|---|
| 分割方式 | Hilbert曲線 → **BSP（再帰的二分割）** |
| 領域の形 | 有機的な連続領域 → **矩形** |
| 領域の面積 | 全員等面積 → **不揃い・ランダム** |
| `region_map` | ピクセル座標の配列 → **矩形1つ（x, y, w, h）** |
| シールの切り抜き | 正方形センタークロップ → **タイルの縦横比に合わせた切り抜き** |
| Phase 2の分配 | 面積按分を含む → **完全均等**（面積が運で決まるため按分は不当） |

矩形の再帰分割はモンドリアンの手法であり、フェルメールから続くオランダ絵画の系譜に乗る。

#### (2) 「絵として成立させる」要件の削除

**シールトは1枚の絵として成立している必要はない。** これに伴い以下を変更する。

| 項目 | 変更 |
|---|---|
| G-5（1枚の絵としての統一感） | **削除** |
| §4.2 手順5「全体調整」 | 統一感のための処理のため**削除**（署名パターンのみ残す） |
| Phase 0の目的 | 美的判断 → **技術検証**（決定性・分割・性能）。所要は4〜6週から1〜2週へ |
| 写真コーパスの収集 | 最優先 → 通常優先 |
| G-4（ピクセルアートらしさ） | **維持する**（下記） |

**G-4を残す理由**: 「SNS生成ピクセルアート＝シールト」という概念の一般化が競合優位性である（§1.2）。絵である必要はないが、ピクセルアートである必要はある。写真の粗いモザイクに見えると、それが何であるかが伝わらない。

**価値の出どころが移動することの明示**: 作品そのものが鑑賞に耐える必要がないなら、毎日見に来る理由は別の場所から供給されなければならない。開封の演出、自分の区画がそこにあること、アーカイブが積み上がること、抽選の結果である。**シールトは「作品」ではなく「証拠」である。** 実装チームが磨くべきはS-04とS-07の体験であり、生成物の美しさではない。

---

**受け入れる帰結**: 公式アトリエの発見手段は招待コードのみとなる。アプリ内に検索・ディレクトリを持たないため、推しは自身のSNS等でコードを配布する。これは「アトリエに入らないと所有できない」というクローズド性（競合優位性）を守る一方、アプリ内での自然発見による成長は起こらない。

## 1. プロダクト定義

### 1.1 一行定義

> **その日を生きた全生命の記録を、1日1枚の写真から自動生成されるピクセルアートとして共同で預かるSNS。**

### 1.2 コンセプトの構造

1. **記録層**: シールダーは1日1枚だけ写真（シール）を投稿する
2. **生成層**: アトリエごとに、その日の全シールから1枚のピクセルアート（シールト）がUTC 00:00に自動生成される
3. **再分配層**: 個々のシールトは無償で手渡される。束ねられた全生命シールトのみが商品となり、売上がその日を生きた全員へ戻る（Phase 3以降）

**Why you**:
働くこと以外に生きる価値を見出せない人に、「今日を生きた」という事実そのものが他者と結合して1つの作品になり、かつ経済的に再分配されるという体験を与える。推し活が「他者への帰属」であるのに対し、Schiildは「自分を含む生態系への帰属」を提供する。

**名称由来**: フェルメール『絵画芸術（De Schilderkunst）』。歴史の女神クレイオを描いた作品であり、「記録」と「絵画」の交点というプロダクト思想と一致する。

### 1.3 SETLOGとの差分表

| 観点 | SETLOG | Schiild |
|---|---|---|
| 投稿単位 | 1時間ごとに2秒動画 | **1日ごとに写真1枚（シール）** |
| 1日の定義 | 04:00〜翌04:00（ローカル） | **UTC 00:00〜24:00（全世界共通）** |
| グループ | ログ（2〜20人、招待コード制） | **アトリエ**（2〜20人、招待コード制、定員は作成時固定） |
| 同一素材の多重投稿 | 不可 | **可**（1枚のシールを複数アトリエへ同時投稿） |
| 生成物 | 縦分割のVlog動画（手動） | **シールト**（UTC 00:00に自動生成されるピクセルアート） |
| 未投稿枠 | 黒画面＋「zzz」 | **未描画セル（VoidCell）** |
| 生成物の帰属 | 各自が端末に保存 | **抽選で1名が「預かる」**（売買はPhase 2） |
| 通貨 | なし | KUUN（Phase 2以降） |
| コミュニティ | 友人12人程度 | クローズド維持＋公式アトリエ（toB） |
| 収益 | なし | **Phase 1はゼロ**。Phase 2以降に導入 |

**踏襲すべきSETLOGのUX的発明（削るとプロダクトが死ぬもの）**:

- **やり直しの効かなさ**: 時刻を過ぎたら遡って投稿できない。この不可逆性が「記録」の重みを作る
- **編集機能をほぼ持たないカメラ**: 加工できないから飾らない日常が出る
- **欠落の可愛さ**: 未投稿を罰ではなく愛嬌として表現する
- **人数で構図が変わる**: 参加人数が作品の形を決める

### 1.4 用語辞書（実装時の命名を統一すること）

| 日本語 | 英語識別子 | 定義 |
|---|---|---|
| シール | `Schiil` | ユーザーが1日1枚投稿する写真 |
| シールダー | `Schiilder` | シールを投稿するユーザー |
| 公式シールダー | `VerifiedSchiilder` | eKYC完了ユーザー（Phase 2） |
| アトリエ | `Atelier` | シールを共有するグループ |
| 公式アトリエ | `OfficialAtelier` | クリエイターが運営する大定員のアトリエ（`ateliers.is_official = true`） |
| シールト | `Schiild` | アトリエ単位で1日1枚生成されるピクセルアート |
| 全生命シールト | `GlobalSchiild` | プラットフォーム全投稿から1日1枚生成される作品 |
| 預かり手 | `Custodian` | 抽選で選ばれ、そのシールトを預かるユーザー |
| KUUN | `Kuun` | 本サービス内のポイント（Phase 2以降） |
| 未描画セル | `VoidCell` | シールが投稿されなかった領域 |
| シールト日 | `SchiildDate` | **UTC 00:00起点**の論理日付（`YYYY-MM-DD`） |

> ⚠️ **`Owner` / `所有者` という語を実装・UIの両方で使わないこと。** §6.4の方針により `Custodian` / 「預かり手」で統一する。

> ⚠️ **`Schiild` は「1枚の生成作品」を指す語として予約する。** アプリ・プラットフォーム自体を指す識別子として使わないこと（`SchiildService` `SchiildModule` `SchiildConfig` などは禁止）。プラットフォーム側は `App` / `Platform` / `Core` を用いる。

**命名の由来**: 全ての語をフェルメール『絵画芸術（De Schilderkunst）』から導く。`Schiil`（投稿物）と `Schiild`（生成作品）は同じ井戸から汲まれた対の語であり、日本語の「シール」「シールト」の韻もこの関係に対応する。`Atelier` はフェルメールの時代の工房を指す体系内の語である。

### 1.5 識別子の取り違えに対する防護策 ★必須

`Schiil` と `Schiild` は末尾1文字しか違わない。これは意図的な命名だが、取り違えは静かに通過してしまうため、以下3点を実装の前提条件とする。

| # | 防護策 | 内容 |
|---|---|---|
| 1 | **型で分ける** | TypeScriptは branded type、Rustは newtype で `SchiilId` と `SchiildId` を別型にする。素の `string` / `UUID` を境界を越えて受け渡さないこと |
| 2 | **外部キーを必ず張る** | SQLには型安全がなく、`schiil_id` と `schiild_id` の取り違えは構文上通ってしまう。全ての参照に FK 制約を張り、実行時に失敗させて気づけるようにする |
| 3 | **省略形を禁じる** | `sid` `sId` `id` のような曖昧な変数名を使わない。ローカル変数でも `schiilId` / `schiildId` と完全形で書く。ESLint / Clippy のルールで機械的に強制すること |

```typescript
// 防護策1の実装例
type SchiilId  = string & { readonly __brand: 'SchiilId' };
type SchiildId = string & { readonly __brand: 'SchiildId' };
// これにより getSchiild(schiilId) はコンパイルエラーになる
```

## 2. コアループとゲームデザイン

### 2.1 デイリーループ

```
[起床〜就寝]
  ユーザー: 今日の1枚を撮る（1日1回のみ）
    ↓
  ユーザー: 投稿先アトリエを選択（複数選択可）
    ↓
  アトリエ画面: 参加メンバーの領域が1つずつ色付いていく（リアルタイム）
    ↓
[UTC 00:00 = JST 09:00]
  システム: 各アトリエの当日シールトを生成（確定）
  システム: 抽選で預かり手を決定（順列を保存）
  システム: 全生命シールトを生成
    ↓
[UTC 00:15 一斉配信]
  プッシュ通知「昨日のシールトが焼き上がりました」
  開封演出（ピクセルが1マスずつ現れる、3秒）
```

**UTC境界とローカル開封の分離について**:
論理日をUTCで固定することで全生命シールトの同時性が担保される。**v1.1では、その同時性を体験にも適用する。**

**開封通知は UTC 00:15 に全ユーザーへ一斉配信する。** 世界中の全員が同じ瞬間に同じ作品を開く。作品が同時であっても配信を各自の朝にずらせば体験は同時ではなくなるため、「その日を生きた全生命の記録」というコンセプトには一斉配信のほうが整合する。

**配信時刻を 00:15 とする理由**: 生成バッチは UTC 00:00 開始で最大15分を要する。00:00 ちょうどに送ると作品がまだできていない。アトリエごとに完了次第送ると最大15分ずれて「一斉」でなくなる。バッチの窓が閉じる **UTC 00:15 を固定の配信時刻**とすることで、同時性と確実性を両立する。

**受け入れる代償**: 各地の生活時間に合わない。JSTでは09:15（通勤時間帯）、CETでは01:15（深夜）となる。SETLOGの04:00が持っていた「誰も起きていない時間に焼き上がっている」という儀式性は得られない。同時性を優先してこれを受け入れる。

**日付ラベル**: UTC日付をそのまま用いる。JSTでもPDTでも、その窓の中で覚醒時間の大半を占めるのはラベル日の日中となるため直感と一致する。ただしアプリ内で「この作品の対象時間: 9/7 09:00 – 9/8 09:00 (JST)」を必ず明示すること。

### 2.2 リテンション設計

| フック | 実装 |
|---|---|
| 連続記録（ストリーク） | 連続投稿日数を表示。途切れても罰を与えない |
| 開封の儀式 | **UTC 00:15の一斉通知**＋3秒の開封演出。全世界が同じ瞬間に開く |
| 欠員の可視化 | 「7/12人が今日を記録しました」。**個人名を出した催促はしない** |
| レアリティの可視化 | 生成直後にレアリティ指標（§4.5）を提示 |
| アーカイブの蓄積 | カレンダー表示で参加シールトがタイル状に増える |
| 抽選の期待 | 毎日1回、誰が預かるかが決まる。運の平等性 |

### 2.3 参加動機の設計

- **初期ユーザー**: 「少人数期のシールトに参加した」希少性 → `participant_count` と `schiild_index` を作品メタデータに恒久記録し、プロフィールに勲章として表示
- **後期ユーザー**: 「推しの公式アトリエに参加した」帰属 → 公式アトリエ、参加証明バッジ、限定展示ページ（Phase 3）

### 3.2 主要テーブル定義（PostgreSQL 16）

```sql
CREATE TABLE users (
  id              UUID PRIMARY KEY,

  avatar_url      TEXT,
  timezone        TEXT NOT NULL DEFAULT 'Asia/Tokyo', -- ★表示専用（対象時間の窓をローカル時刻で示すため）
```

### 3.3 論理日の算出

```sql
-- UTC 00:00起点。schiild_date は単純に timestamptz の UTC 日付。
CREATE FUNCTION to_schiild_date(ts TIMESTAMPTZ) RETURNS DATE AS $$
  SELECT (ts AT TIME ZONE 'UTC')::DATE;
$$ LANGUAGE SQL IMMUTABLE;
```

UTC固定としたことで、この関数は自明になった。**ただしユーザーへの表示は必ずローカル時刻の窓（開始〜終了）を併記すること。** 日本のユーザーにとって「1日」は朝9時始まりであり、説明なしでは必ず混乱する。

## 4. シールト生成エンジン仕様 ★本プロダクトの心臓部

### 4.1 要件

| # | 要件 |
|---|---|
| G-1 | **決定性**: 同じ入力からは常に同一の出力。バイト単位で一致すること |
| G-2 | **参加人数非依存**: 1人でも200人でも破綻しない分割 |
| G-3 | **可読性**: 誰がどこを描いたかを後から示せる（`region_map`） |
| G-4 | **ピクセルアートらしさ**: 固定パレット・ハードエッジ。**写真モザイクに見えてはいけない** |
| ~~G-5~~ | ~~1枚の絵としての統一感~~ → **v0.5で削除。絵として成立させる必要はない**（§0.4-2） |
| G-6 | **性能**: 1アトリエ200ms以内、全アトリエをUTC 00:00〜00:15で完了 |
| G-7 | **部分再生成の安定性**: シールを1枚除去した再生成で、他の領域が変化しないこと |

### 4.2 アルゴリズム v1.0.0

```
入力:
  atelier_id, schiild_date, capacity
  schiils: [(user_id, slot_index, image_sha256, image_bytes)]
  frozen_seed: Option<hex>    ← 再生成時に既存の generation_seed を渡す
  palette: 32色

出力:
  schiild.png (1024x1024), thumbnail.png (256x256),
  region_map.json, metadata.json

手順:
  1. シード決定 ★v0.2で変更
     if frozen_seed.is_some():
         seed = frozen_seed          # 再計算しない
     else:
         seed = SHA256(algorithm_version || atelier_id || schiild_date
                       || concat(sorted(all_slot_image_sha256)))
     rng = ChaCha20(seed)

     ※ 再生成時にシードを再計算すると、除去したタイルだけでなく
        BSPの分割そのものが変わり、構図が丸ごと入れ替わる。
        G-7を満たすため、シードは初回生成時に確定させ以後不変とする。

  2. 矩形分割（BSP / 再帰的二分割）★v0.5で変更
     rects = [{x:0, y:0, w:128, h:128}]
     while rects.len() < capacity:
         # 面積上位45%からランダムに1つ選ぶ（極端な細片化を防ぐ）
         target = rng.choice(rects.sorted_by_area_desc()[0 .. max(1, len*0.45)])
         axis   = if target.w >= target.h { vertical } else { horizontal }
         cut    = round(len/2 + (rng()*2-1) * variance * len * 0.34)
         cut    = clamp(cut, 1, len-1)
         split target into two rects at cut

     - 分割は整数格子上で行う（サブピクセルを作らない）
     - variance はアトリエ共通の定数（初期値 0.55）
     - 生成された矩形を rng でシャッフルし slot_index へ割り当てる
     - 未投稿スロットの矩形は VoidCell として確保する

     ※ 面積は不揃いになる。ある日は画面の1/3、ある日は隅の細片になるが、
       日ごとにランダムに変わるため長期的には均される。
       この不均等さがあるため、Phase 2の分配に面積按分を用いてはならない（§5.6）。

  3. 各シールの描画
     a. ★入力は常に 1080x1080（§4.9）。タイルの縦横比に合わせてセンタークロップする
     b. area-average でタイル寸法へ縮小
     c. Oklab空間へ変換し32色パレットへ最近傍量子化
     d. Floyd–Steinberg誤差拡散（強度は設定可能。§4.3の注意参照）
     e. タイル矩形へ合成（マスク不要）

  4. VoidCell
     - パレット最暗色 + rng由来のノイズテクスチャ
     - 「消えかけた」印象。罰の記号にしない
     - ★大きな矩形が VoidCell になる日は作品に大きな穴が空く。
       これを許容する（絵として成立させる必要はないため）

  5. 署名
     - 4隅にアルゴリズムバージョンの4px署名パターンを埋め込む
     ※ v0.4までの「全体調整」（平均色相の乗算・境界の無輪郭化）は
       絵としての統一感を作るための処理であったため、v0.5で削除した

  6. 出力（8倍ニアレストネイバー拡大）

  ※ タイル間の余白（ガター）を 0〜3px 入れるかは未決（§13）。
    0 は写真が地続きになり抽象画に近づく。1以上は各区画が独立して
    「N人が並んでいる」という読み方になる。
```

### 4.3 パレット定義（`schiild_32`）

**方針: 知覚的に等間隔な汎用32色（写真の再現性優先）。**

構築手順:
1. 日常写真のコーパス（1万枚以上、時間帯・季節・屋内外を分散させる）を用意
2. Oklab空間でk-means（k=32）を実行
3. 得られた32色から、無彩色6段（純黒〜純白）を強制的に含むよう調整
4. 隣接色のOklab距離が過度に偏らないよう手動で微調整

**⚠️ 重大な副作用と対処**:
知覚等間隔の32色は写真を素直に再現してしまうため、**出力が「ピクセルアート」ではなく「粗い写真モザイク」に見えるリスク**がある。これはG-4への直接的な脅威である。Phase 0の評価では以下を必ず検証すること。

- 実効解像度を下げる（128x128 → 96x96 等）と記号性が上がるか
- ディザ強度を上げる（0.6 → 0.8 / 1.0）とピクセルアートらしさが増すか
- 逆にディザを完全に切る（0.0）とフラットな色面が出て記号的になるか
- 量子化前に軽い posterize / 彩度ブーストを入れると改善するか

これらをパラメータとして外出しし、Phase 0で人間が比較評価できるようにすること。

**将来拡張**: `palette_id` をアトリエ属性として保持しているため、Phase 4で公式アトリエ／IPコラボ用の専用パレットを配布できる。

### 4.4 全生命シールト（GlobalSchiild）の生成

```
1. 当日の承認済み全シールを取得
2. 各シールを 1px に縮約（Oklab平均色）
3. SHA256(image_sha256 || schiild_date) % 65536 でバケット割当
   → 256x256 キャンバスの各ピクセルに対応
4. 同一バケット内の色を Oklab で平均し、パレット量子化
5. 空バケットは近傍4ピクセルの補間で埋める
6. 4倍拡大して 1024x1024 で出力
7. 各ユーザーの「自分のピクセル座標」を索引可能な形で保存
```

**Phase 1での位置づけ**: **非売**。運営が保有し、閲覧のみ提供する。販売と再分配はPhase 3で導入する（§5.5）。

### 4.5 メタデータとレアリティ指標

生成時に算出し `schiilds.metadata` へ保存。**生成時の値を固定し、後から再計算しない。**

```json
{
  "participant_count": 7,
  "capacity_at_gen": 12,
  "fill_rate": 0.5833,
  "is_perfect": false,
  "schiild_index": 128,
  "palette_histogram": { "c00": 0.12, "c01": 0.03 },
  "dominant_hue": 214.5,
  "color_entropy": 4.21,
  "symmetry_score": 0.33,
  "void_ratio": 0.4167,
  "algorithm_version": "v1.0.0"
}
```

| 指標 | 希少性への寄与 |
|---|---|
| `is_perfect` | 高（「全員が生きていた日」） |
| `schiild_index` | 若い番号ほど高（初期参加動機を支える） |
| `participant_count` | 少人数＝初期性 / 大人数＝祝祭性 |
| `void_ratio` | 0.0と高欠落の両端で希少 |

### 4.6 実行基盤

- **UTC 00:00** に日次バッチ起動
- アトリエ単位でジョブをキュー投入し、ワーカーで並列処理
- **冪等性**: `(atelier_id, schiild_date)` でユニーク制約。再実行しても同一結果
- **失敗時**: 3回リトライ後DLQ。失敗アトリエには「生成に失敗しました。再生成中です」と正直に表示する。**偽の作品や代替画像を出してはいけない**
- ★**UTC 00:15 に全ユーザーへ一斉配信する。** ユーザーごとの予約配信を行わない
- 生成が15分以内に完了しなかったアトリエの参加者へは、開封通知ではなく生成失敗の通知（S-10相当）を送る
- ★**同時刻に全ユーザーへ配信するため、ファンアウトの瞬間的な負荷が最大になる。** キューを分割し、配信自体は数分内に収まるよう設計すること（配信の完了時刻ではなく、開始時刻が 00:15 であればよい）
- 実装言語: Rust推奨。決定性のため浮動小数点演算の順序を固定し、並列化しても結果が変わらないこと

### 4.7 削除要請への対応 ★v0.2で新設

写り込み・権利侵害等で特定のシールに削除要請があった場合の手続き。

```
1. 対象シールを特定し schiils.removed_at を記録
2. そのシールが含まれる全シールトを列挙
3. 各シールトについて:
   a. 現行版を schiild_revisions へ退避（image_key を保持）
   b. frozen_seed = 既存の generation_seed を渡して再生成
      → 該当領域のみ VoidCell 化。他の領域はバイト単位で同一（G-7）
   c. schiilds.revision をインクリメントし、新しい画像で更新
   d. 預かり手へ「作品の一部が権利上の理由で除かれました」と通知
4. 旧版は created_at + 90日 で画像実体を破棄（purged_at を記録）
   異議申立が係属中は dispute_open = true とし、期限の進行を停止する
5. 破棄後も schiild_revisions の行は残す（監査証跡）
```

**★除外されたシールを作品へ戻すことはできない**（v0.7で確定）。モデレーションで除外されたシールは、その日のシールトに永久に含まれない。異議申立を廃止したため（§10.4）、判定後に区画を埋め直す再生成は行わない。「一度確定した作品を描き直さない」という原則を、除外にも等しく適用する。

**保管期間90日の根拠**: 異議申立期間との整合。旧版には削除要請の対象物そのものが含まれるため、永久保管はそれ自体がリスクとなる。**この期間設定は法務レビューを経て確定すること。**

### 4.8 規模に応じたレンダリング階層 ★v0.4で新設

ギルドを廃止したことで、公式アトリエは大定員を収容する必要がある。しかしキャンバスを無制限に拡げることはできない。

**制約の構造**: 128×128 は 16,384 ピクセルであり、定員200人なら平均82ピクセル（約9×9）しか割り当たらない。矩形分割では面積が不揃いになるため、最小のタイルはこれよりさらに小さくなる。定員を増やすにはキャンバスを拡げるしかないが、現在は128×128を8倍拡大して1024pxで出力することで「粗いドット」の見た目を作っている。キャンバスを256にすれば拡大率は4倍、1024にすれば等倍となり、階層を上げるたびにドットが半分ずつ小さくなって、最終的にただの画像になる。**これはG-4（写真モザイクに見えてはいけない）への直接的な脅威である。**

**解決**: 規模に応じて2つのアルゴリズムを切り替える。バケット方式は §4.4 の全生命シールトで既に定義済みのものを流用する。

| `render_tier` | 定員 | 方式 | キャンバス | 拡大率 | 1人あたり |
|---|---|---|---|---|---|
| `bsp_128` | 2〜200 | 矩形分割（§4.2） | 128×128 | ×8 | 82px〜 |
| `bsp_256` | 201〜800 | 矩形分割（§4.2） | 256×256 | ×4 | 82px〜 |
| `bucket` | 801〜 | バケット割当（§4.4） | 256×256 | ×4 | 約1px |

- `render_tier` はアトリエ作成時に `capacity` から決定し、以後変更しない
- `bucket` 階層では「自分の領域」が「自分のピクセル」になる。これは §6.2 S-07 で最も感情的なピークとして設計した体験そのものであり、破綻ではなく収束と位置づける
- `bucket` 階層でも `region_map` は保存する（1ユーザー1座標）
- **Phase 0で `bsp_256` の見た目を評価すること。** 拡大率が4倍に落ちた時点でピクセルアートらしさが失われるなら、`bsp_256` を廃して200人超は全て `bucket` とする

### 4.9 シールの入力仕様 ★v1.2で新設

**シールは、アプリ内カメラで撮影した画像のみとする。** ギャラリーからの選択、外部アプリからの共有、ファイル添付をいずれも実装しない。

| 項目 | 値 |
|---|---|
| 入力手段 | **アプリ内カメラのみ** |
| 寸法 | **1080 × 1080**（全ユーザー共通・固定） |
| 形式 | JPEG / 品質85 |
| メタデータ | EXIFを一切書き込まない。位置情報の権限を要求しない |
| 1枚あたり | およそ150〜250KB |

**正規化の必須要件**: 端末とカメラによって native 解像度は異なり、特にインカメラは1080に満たないことがある。**撮影後、クライアント側で必ず 1080×1080 へ正規化してからアップロードする**（不足時は拡大、超過時はセンタークロップ後に縮小）。サーバはこれ以外の寸法・形式を受け付けない。

**この決定の効果**:

1. **EXIF判定の仕組みが不要になる。** v1.1まで「当日のEXIFを持つ写真のみ許可」という判定を置いていたが、撮影日時の検証そのものが不要になる。位置情報の漏洩対策も、権限を要求しないだけで済む
2. **寄与の質が全員で等しくなる。** 高精細な写真と古い端末の写真が同じ作品に混在しない。抽選確率の一律（§5.1）、還元の完全均等（§5.6）と同じ原則を、画像そのものにも適用する
3. **生成パイプラインが単純化する。** 入力寸法が常に一定なので、タイル縦横比へのクロップと area-average 縮小の挙動が予測可能になる

**⚠️ 受け入れるリスク（重要）**:

**アプリ内カメラが唯一の入口であるため、カメラが動かなければその日の記録は永久に失われる。** 権限の拒否、端末固有の不具合、撮影中のクラッシュ、いずれもその日を消す。1日1枚で取り返しがつかない設計であるため、**カメラの実装品質が記録の保全に直結する**。以下を必須とする。

- 権限拒否の状態を明示的に実装し、設定アプリへの導線を置く
- 撮影〜正規化〜アップロードの各段階で失敗を検知し、リトライを可能にする
- アップロード失敗時、正規化済みの画像を端末にローカル保持し、締切まで再送を試みる
- カメラの起動失敗率・撮影失敗率を主要な監視指標として計測する

**アクセシビリティ上の注意**: OS標準カメラの支援機能に依存している利用者は、アプリ内カメラでは同等の操作ができない可能性がある。WCAG 2.2 AA（§7）の観点で、撮影操作の代替手段を検討すること。

## 5. 経済圏設計（Phase 1は無償・無課金）

> **Phase 1では金銭が一切動かない。** 一次配布は無償、KUUNなし、課金機能なし、全生命シールトも非売。本章の大半はPhase 2以降の設計である。

### 5.1 預かり手の決定（抽選）

```
[UTC 00:00 生成時]
  1. サーバーCSPRNGで lottery_seed を生成し保存
  2. lottery_seed から参加者全員の順列（lottery_order）を確定させ保存
     ★辞退のたびに引き直さない。順列は生成時に一度だけ確定する
  3. 順列の1番目を預かり手として schiild_custody へ登録
  4. lottery_seed を作品詳細で公開し、誰でも順列を再計算・検証できるようにする
```

**当選確率は参加者一律とする。** 連続投稿日数などで重み付けしてはならない。「生きたこと自体に価値がある」というWhyを、努力で傾けられる仕組みが裏切るため。

**`generation_seed` を抽選に流用してはならない。** `generation_seed` は投稿画像のハッシュから導出されるため、理屈のうえでは画像を作り直して当選を引き当てる余地が残る。Phase 1は金銭価値がないので実害はないが、Phase 2で二次流通が始まった瞬間に攻撃対象になる。後付けが困難なため、初回実装から `lottery_seed` を分離すること。

### 5.2 辞退と繰下げ

```
預かり手が「辞退する」を実行
  → 即時に lottery_order の次点者へ繰下げ
  → schiild_custody_events に 'declined' と 'promoted' を記録
  → 全員が辞退した場合はアトリエ共同保管（custodian_user_id = NULL）
```

**受取期限は設けない（Phase 1）。** 当選者がアプリを開かなければ預かりは宙吊りのままとなるが、Phase 1には売買がないため実害は所有者クレジットの表示のみである。

**⚠️ Phase 2での追加規則**: 二次流通の導入時に「アカウント休眠90日で預かりを解除し、アトリエ共同保管へ戻す」規則を追加すること。休眠判定には `users.last_active_at` を用いる。これを入れずに経済圏を稼働させると、死蔵された作品が市場に穴を空ける。

### 5.3 「預かる」ことに伴う権利（Phase 1）

| 権利 | 実装 |
|---|---|
| **プロフィールへの展示権** | マイページに預かり中のシールトをタイル表示 |
| **所有者クレジット表示** | シールト詳細に「◯◯さんが預かっています」と表示 |
| **カバー画像設定権** | そのシールトをアトリエのカバー画像に設定できる |

**書き出しは預かり手であっても常に透かし入りとする。** 高解像度・透かしなしの書き出しは提供しない。渡されるのは所有物ではなく「記録の管理者という立場」であるという設計を、機能レベルで一貫させるため。副次的に、共有される画像が必ずブランドを帯びて拡散する。

**カバー画像の競合ルール**: 複数の預かり手が設定を試みた場合、直近に設定した者が反映される。`cover_set_by` と `cover_set_at` に履歴を残し、アトリエ運営者はいつでも解除できる。

### 5.4 KUUN仕様（Phase 2以降）

| 項目 | Phase 2 | Phase 4以降（要法務判断） |
|---|---|---|
| 位置づけ | 譲渡不可・換金不可のポイント | 暗号資産化を検討 |
| 最小単位 | 1 KUUN（内部は1/1000精度の整数） | 同左 |
| 取得方法 | 二次流通の手数料還元、全生命シールト売上の分配 | ＋購入 |
| 用途 | シールト取得、認証費用の支払い | ＋外部決済 |
| ユーザー間送金 | **不可** | 検討 |
| 換金 | **不可** | 要交換業登録 |
| 利用資格 | 公式シールダー（Tier2）のみ | 同左 |

Tier2未満のユーザーへの還元は「未確定KUUN」として保持し、Tier2昇格時に確定させる。これが認証費用の支払い動機になる。

### 5.5 全生命シールトと再分配（Phase 3）

**一次配布を無償化したことで、再分配の燃料が一次流通から消えた。** 個々のアトリエのシールトは無償で手渡されるため、法定通貨がシステムへ流入する経路は以下に限られる。

1. **全生命シールトの外部販売** ← 主エンジン
2. アレンジアート販売
3. IPコラボ
4. 認証費用・公式アトリエ作成費用（分配には回さない運営収益）

したがって**全生命シールトは、サイドの収益源ではなく再分配エンジンそのものである。** これはコンセプトに素直に接続する構造でもある。個々のシールトは「生きたことへの贈与」として無償で手渡され、それらが束ねられた全生命シールトだけが商品になり、売上がその日を生きた全員へ戻る。

**Phase 1での扱い**: 販売しない。閲覧のみ提供し、「現在このシールトは販売していません」と明示する。

### 5.6 二次流通（Phase 2）

- 同一アトリエの**現メンバー間でのみ**譲渡可能
- 手数料の一部を参加シールダーへKUUN還元
- ★**還元は参加シールダー間で完全均等に分配する。** 面積按分を用いてはならない。
  矩形分割によりタイル面積は運で決まるため（§4.2 手順2）、
  面積に応じて分配すると「たまたま大きな区画を引いた人が多く受け取る」ことになり、
  「生きたこと自体に価値がある」というWhyを裏切る（§5.1の抽選確率一律と同じ理由）
- 端数は切り捨て、余りはプラットフォーム勘定へ記録する
- 退会時は「①アトリエへ返還する ②預かりを解除しアーカイブ化」の2択。塩漬けにしない
- アトリエ解散時は全シールトがアーカイブ化され、記録のみ残る

### 5.7 定員（capacity）の扱い

**Phase 1: 作成時に固定、変更不可。**

**Phase 2以降で有料拡張を導入する場合の規則**:
- 拡張は**一方向のみ**（縮小不可）。縮小するとスロットが孤児化する
- 適用は**翌シールト日から**。過去作品は `capacity_at_gen` により当時の構図を保持
- **既存メンバーの持ち分が薄まる**（12人→50人で1人あたりの描画領域は1/4になる）。運営者が支払うと参加者の取り分が減る構造であるため、運営者の一存で実行できない設計とすること（メンバー通知を必須とし、一定割合の同意を要件とするなど）

### 5.8 キャッシュポイント（Phase 2以降）

| # | 収益源 | 導入フェーズ |
|---|---|---|
| 1 | 公式シールダー認証費用 | Phase 2 |
| 2 | 二次流通の手数料 | Phase 2 |
| 3 | 定員の有料拡張 | Phase 2 |
| 4 | 全生命シールト販売 | Phase 3 |
| 5 | アレンジアート販売 | Phase 3 |
| 6 | 公式アトリエ作成費用（定員帯による価格差あり） | Phase 3 |
| 7 | IPコラボ | Phase 4 |

**Phase 2着手時に必ず実施すること**: ストア手数料（Apple/Google 15〜30%）を織り込んだ分配率の再計算と、IAP／Web決済の導線設計。デジタルコンテンツの販売はアプリ内課金を経由する必要がある可能性が高く、これは分配率の前提を壊しうる。**Phase 1を無課金としたことで、この検証をPhase 1の期間中に前倒しで行える。**

### 6.2 主要画面

> **v0.7でモックを作成し、以下の各画面に具体的な決定を反映した。** 数値・文言はモックで検証済みのものであり、実装時はそのまま使うこと。

#### S-01 ホーム（アトリエ一覧）
- 右上に `＋` → 「アトリエを作成」「参加コードで参加」（SETLOG踏襲）
- カードに: アトリエ名 / メンバーアバター列 / 本日の投稿状況インジケータ（自分が投稿済みなら塗りつぶし） / 「7/12人が今日を記録しました」 / 直近3日分のサムネイル
- ソロモード切替（SETLOG踏襲）: 下部スイッチで「自分だけのアトリエ」へ

**v0.7の決定**:
- 投稿状況インジケータは**1辺9pxの正方形**とする。塗りつぶし=投稿済み、輪郭のみ=未投稿。丸ではなく四角にするのは、シールトのタイルと形の語彙を揃えるため
- カードは `ATELIER 04` の等幅ラベル → アトリエ名（17/500）→ `7 of 12 が今日を記録`（等幅12）→ 直近3日のサムネイル（44px、角丸0）の順
- ソロアトリエは等幅ラベルに `／ SOLO` を付す

#### S-02 アトリエ詳細（本日のキャンバス）
- 上部: 矩形分割のタイルが輪郭線だけで表示され、**投稿済みのタイルだけが色付く**
  - SETLOGの「分割グリッドが埋まっていく」体験の翻案。タイルの大きさが日ごとに違うため、埋まり方が毎日変わる
  - WebSocketでリアルタイム更新。誰かが投稿すると領域がふわっと色付く
- 中部: **UTC 00:00までのカウントダウン**。あわせて「この作品の対象時間: 9/7 09:00 – 9/8 09:00 (JST)」を明示
- 下部: メンバー一覧（投稿済み/未投稿）。**未投稿者を名指しで責める表現は禁止**
- 過去のシールトへは横スワイプで遡れる

**v0.7の決定**:
- 本日のキャンバスは、未投稿タイルを**輪郭線（1px `--sc-line-strong`）のみ**で描く。今日の構図をあらかじめ示すことで「あと5枚でこの形が埋まる」が一目で分かる
- カウントダウン（等幅22）と対象時間の窓（等幅11）を必ず併記する。UTC境界により日本では朝9時が区切りになるため、窓の明示がないと必ず混乱が起きる
- ★**メンバー一覧はアバターや名前を表示せず、無地の30px角丸8px矩形で表す。** 投稿済みは塗り（`--sc-sunken`）、未投稿は破線の枠のみ。**誰が欠けているかを識別できないようにすること。** 顔や名前を並べると未投稿者が名指しで可視化され、§2.2で禁じた催促の圧が生まれる。分かるのは人数だけでよい

#### S-03 撮る（カメラ）
- **加工機能をほぼ持たない（SETLOG思想の厳守）**: インカメ/アウトカメ切替、フラッシュのみ。フィルタ・美肌・トリミングなし、正方形固定
- 撮影後: プレビュー → キャプション（任意・50文字）→ 投稿先アトリエ選択（複数可）→ 確定
- **確定後は取り消せない。** 確定前に強い確認ダイアログ（「今日のシールは一度きりです」）
- 本日投稿済みの場合: 「今日のシールはもう描かれています」と表示し、**追加投稿先の選択のみ**可能
- ★**ギャラリーからの選択を実装しない**（v1.2で廃止）。アルバムへの導線を置かない
- ★**権限拒否の状態を必ず実装すること。** アプリ内カメラが唯一の入口であるため、権限が拒否されているとその日の記録が不可能になる（§4.9のリスク参照）

**v0.7の決定**:
- ★**画面に置かないものが重要。** フィルタの帯、明るさ調整、比率切替、**アルバムへの導線**を一切置かない。存在するのはシャッター、内外カメラ切替、フラッシュ、日付（等幅11）のみ
- ★入力はアプリ内カメラのみ。撮影後は 1080×1080 へ正規化する（§4.9）
- シャッターは**72pxの角丸8px正方形**（`--sc-fill`）。丸にしないのはアプリ全体の形の語彙に合わせるため
- 確認ダイアログの見出しは**操作の確認ではなく事実の告知**にする。「本当に投稿しますか」ではなく「**今日のシールは一度きりです**」。本文で投稿先を名指しで読み上げ、差し替えができないことを明言し、残り時間を添える
- 確定ボタンは黒、戻るは白。破壊的操作ではないので赤は使わない。押し間違いを減らすため縦に並べて離す

#### S-04 シールト詳細
- 生成演出: 初回表示時、タイルが1枚ずつ現れるアニメーション（3秒）
- 表示: 作品画像 / schiild_index / 参加者アバター / レアリティ指標 / **預かり手のクレジット** / 対象時間の窓
- 「領域マップを見る」: 各領域に参加者アバターをオーバーレイし、**自分の領域をハイライト**（帰属感の中核体験）
- 「抽選を検証する」: `lottery_seed` と順列を表示し、再計算手順を示す
- 書き出し: **常に透かし入り**（アトリエ名・日付・参加人数）

**v0.7の決定**:
- 未描画セルは生成後、**暗色（`#1C1B18` 相当）で塗る**。前画面で輪郭線だけだったタイルが闇になる。12人中7人の日は作品の4割が沈むが、これを罰ではなく事実として置く
- メタデータは等幅の2カラムで、通算・欠落率・パレット・階層を並べる。**達成率ではなく記録簿の書式で書く**
- 操作は「領域を見る」（黒）→「書き出す」「抽選を検証」（白・横並び）→「預かりを辞退する」（赤枠）の順
- ★**辞退のみ `--sc-danger` を使う。** 押した瞬間に次点者へ権利が移り取り返しがつかないため、他の操作と同じ見た目にしてはならない

#### S-07 全生命シールト
- 本日の全生命シールト（全ユーザー共通）
- 「あなたのシールは、この作品の◯◯番目のピクセルとして記録されています」→ **該当ピクセルへズームする演出**
  - **本プロダクト最大の情緒的ピーク。実装の優先度を最高にすること**
  - ズームは連続的に。ピクセルが特定される瞬間に間（ため）を作る
- 累計参加人数、本日の総投稿数
- 「現在このシールトは販売していません」と明示

**v0.7の決定**:
- ★**拡大鏡を常設する。** 全体像（288px / 72×72の密なピクセル）の下に、自分のピクセルの9×9近傍を12倍で拡大した108pxの窓を置き、中心の1マスを2pxの黒枠で囲う。全体の一点と、その一点そのものを同時に見せる
- 全体像の側にも、自分のピクセル位置に細い黒枠を描く
- 座標（`x 156 ／ y 214`）を等幅で添える
- 統計は等幅2カラムで総投稿・アトリエ数・累計
- Phase 1では画面下に「**現在このシールトは販売していません**」を静かに置く

#### S-08 空状態（アトリエが1つもない）★v0.7で新設

- ★**謝罪しない。** 「まだアトリエがありません」ではなく「**最初のアトリエをつくる**」から始める
- 中央に104pxの2×2の空枠（輪郭線のみ）。これから埋まるキャンバスの比喩
- 本文は2行程度。「アトリエは、誰かと一緒に1日1枚を残す場所です。毎朝ひとつの作品が生まれます。」
- ★等幅で「**ひとりでも始められます**」を添える。Schiildの最初の壁は「誘う相手がいない」ことであり、ソロで開始できることを最初の画面で示す
- 操作は「アトリエをつくる」（黒）／「コードで参加する」（白）

#### S-09 本日投稿済み（カメラタブ）★v0.7で新設

- ★**シャッターを無効化するのではなく、存在させない。** 無効化されたボタンは「押せるはずのもの」を想起させるが、無い機能は問い返されない
- 今日のシール（88px）＋「今日のシールはもう描かれています」＋記録時刻（等幅11、例: `07:12 に記録`）＋キャプション
- `POSTED TO`（投稿済みアトリエ、チェック付き）と `ADD TO`（未投稿アトリエ、チェックボックス）を分けて並べる
- 「追加する」は未選択時、グレーアウトではなく**線と文字を弱めた休止状態**にする

#### S-10 生成失敗 ★v0.7で新設

- ★**仮画像もスピナーも置かない。** 作品の位置は `--sc-sunken` の面のままとし、中央に等幅で `REGENERATING` とだけ表示する。§4.6の「偽の作品や代替画像を出してはいけない」の実装。ここに何か描くと、本物が出たときユーザーは二度見ることになる
- ★**最も知りたいことは「今日の記録は消えたのか」である。** 「7人分のシールは保存されているので、記録が失われることはありません」を必ず明記する
- 再試行回数（`2 of 3`）と次の試行までの時間を等幅で開示する。隠さないほうが不安が小さい
- 画面が死なないよう、下部に過去のシールトを並べる

#### S-11 モデレーション除外の通知 ★v0.7で新設

- ★**責める構造を避ける。** 「違反しました」ではなく「**作品に含められませんでした**」。主語を人ではなく判定に置く
- ★**判定の可謬性に言及しない。** 異議申立を廃止したため（§10.4）、「誤りのこともあります」と認めながら手段を与えないのは、認めない場合より不誠実になる
- 代わりに**不可逆性そのものを理由として示す**。「Schiildでは、一度確定した作品を描き直すことはありません。明日の1枚から、また記録できます。」これは投稿が取り消せないという既存の原則と同じ規則であり、権利の拒否ではなく全員に等しくかかる規則として提示できる
- シールが削除されていないこと、どのアトリエでどう影響したかを具体的に示す
- ★**画面に主要操作を置かない。** 残るのは「シールを見る」（白）のみ。行き止まりにしないため、最後の一文で明日へ接続する

#### S-12 マイページ ★v0.9で新設

- ★**他人と比べる数字を1つも置かない。** フォロワー、いいね、ランキングを実装しないだけでなく、比較対象が構造として存在しない状態にする。比較できるのは過去の自分だけ
- 表示する数値は3つのみ: **連続 / 参加 / 預かり**（等幅22、`--sc-sunken` のメトリックカード）
- ハンドルと開始日を等幅で（`@minato ／ SINCE 2025-11-02`）
- `IN CUSTODY` に預かり中のシールト（88px、角丸0）
- 下部にアーカイブ・設定への行リンク

#### S-13 アーカイブ ★v0.9で新設

- 月単位の7列グリッド。参加した日はその日のシールトのサムネイル、**参加しなかった日は輪郭線のみの空枠**
- ★**空白の日を詰めない。** 飛んだ日は飛んだまま残す。詰めて表示すれば連続した達成の列に見えるが、欠落を隠すと「途切れたことが恥ずかしい」という含意が生まれる。§2.2の「途切れても罰を与えない」を成立させるには、隠さないほうが誠実である
- 画面下に「**記録しなかった日も、そのまま残ります。**」を添える
- 統計は等幅で 今月（`22 of 30`）／通算／最長
- ★**最長記録を現在の連続記録と並べて出す。** 現在が最長を下回っていてもそのまま表示する。隠すと現在の数字が重くなる

#### S-14 アトリエ作成 ★v0.9で新設

- 名前入力（`--sc-sunken` の入力欄）
- 定員は 2 / 5 / 12 / 20 のセグメント選択。選択に連動して**その人数での構図プレビュー（輪郭線のみ）と1人あたりの平均ピクセル数**を表示する
- 注意書き: 「定員はあとから変えられません」＋「過去の作品と構図を揃えるため、作成時に固定されます」
- ★**モーダルで確認を取らない。** §6.6の重みづけに従う
- ★**警告より結果を見せる。** 「変えられません」と繰り返すより、2人と20人で構図がどれだけ違うかを目で見せるほうが判断を誤りにくい

#### S-15 コード参加 ★v0.9で新設

- 8文字のコード入力（等幅18、1文字ずつ枠に区切る）
- コードが有効なら、アトリエのプレビュー（等幅ラベル／名前／`定員 5 ／ 現在 3人 ／ 通算 84枚`／直近4日のサムネイル）を表示する
- ★**「明日から」を必ず明記する。** 「参加すると、明日からあなたの区画が加わります。今日のシールトには反映されません。」
  1日1シールの制約と、当日の作品が確定していく仕組みの帰結だが、書いておかないと「参加したのに自分がいない」という不信を招く

#### S-16 設定 ★v1.0で新設

- セクションは `ACCOUNT` / `NOTIFICATIONS` / `ABOUT` / （無名の最終ブロック）の4つ
- **トグルはピル型にせず、角丸8pxの矩形とする。** ノブは角丸6pxの20px正方形。アプリ全体で唯一の完全な丸みを持つ部品を作らないため
  - オン: `--sc-fill` の塗り／ノブ白
  - オフ: `--sc-line-strong` の輪郭線のみ／ノブ `--sc-line-strong`
- 通知トグルは4つ: シールトができたとき／預かり手に選ばれたとき／全員が揃いそうなとき／今日のシールの前に
- ★通知セクションの下に「**他の人が記録したかどうかは、通知に含まれません。**」を必ず置く。機能説明ではなく設計思想の明示であり、催促されない場所であることを設定画面で保証する
- 「アカウントを削除する」のみ `--sc-danger` の文字色

#### S-17 アカウント削除 ★v1.0で新設

- 見出しは「削除すると、元に戻すことはできません。」
- ★**「消えるもの」と「作品に残るもの」を2枚のカードに分けて対比で示す。** 散文で書くより誤解が少ない
  - 消えるもの: 投稿したシールの原本／プロフィールと連続記録／預かっているシールトの預かり
  - 作品に残るもの: 生成済みのシールトの中の、あなたの区画
- ★残るほうには**その人の実際の記録日数を入れる**（「あなたが記録した311日は、そのアトリエの作品の中に残ります」）。抽象的な規約文ではなく、当人の記録として提示する
- 確認としてハンドルの入力を求める
- 削除ボタンは **`--sc-danger` の塗り**。アプリ全体で唯一の彩度を持つ塗りとする

**赤の3段階**（この順序を崩さないこと）:

| 段階 | 表現 | 該当 |
|---|---|---|
| 弱 | `--sc-danger` の文字色 | 設定内の「アカウントを削除する」行 |
| 中 | `--sc-danger` の輪郭線 | 預かりの辞退（S-04） |
| 強 | `--sc-danger` の塗り | アカウント削除の実行（S-17） |

### 6.6 不可逆性の重みづけ ★v0.9で新設

このプロダクトには取り消せない操作が複数ある。**すべてを同じ強さで警告してはならない。** 全部をモーダルにすると、本当に取り返しのつかない場面での重みが薄れる。

| 重み | 性質 | 扱い | 該当 |
|---|---|---|---|
| **代替不能** | やり直す手段がない | **モーダルで確認する。** 見出しは操作の確認ではなく事実の告知にする | シールの投稿確定（S-03）、預かりの辞退（S-04） |
| **代替可能** | 作り直せるが手間が生じる | **モーダルを出さない。** 選択の隣に注意書きを置き、選択の結果を先に見せる | アトリエの定員（S-14） |

- 投稿は代替不能である。その日は二度と来ない
- 定員は代替可能である。間違えたら別のアトリエを作ればよく、失うのは招待のやり直しの手間だけ

### 6.5 開封演出 ★v0.8で新設

UTC 00:00 に確定した作品を、**UTC 00:15 の一斉通知**で全世界が同じ瞬間に開く。**このプロダクトで最も設計意図が込められた瞬間であり、実装の優先度は S-07 と並んで最上位とする。**

#### 未開封の状態

- 作品の位置は `--sc-sunken` の空面のままにする。プレビューを一切見せない
- 「昨日のシールトが焼き上がりました」＋日付（等幅11）＋「ひらく」（黒ボタン）

#### 再生（三拍構成）

| 拍 | 内容 | タイミング |
|---|---|---|
| 1 | **タイルが1枚ずつ置かれる** | 120ms後に開始、**230ms間隔**。12枚で約2.8秒 |
| 2 | 記録（アトリエ名・日付・`7 of 12`）が現れる | 全タイル完了の**500ms後**、500msでフェード |
| 3 | 預かり手（`CUSTODY` ＋ 名前）が現れる | さらに**1000ms後**、600msでフェード |

#### 動きの原則

- ★**タイルの出現にトランジションを付けない。** フェードインではなく、その瞬間に置く。滑らかにすると画面効果になり、離散的にすると「一枚ずつ置かれている」手触りが出る
- ★**出現順はランダム**（シードから決定）。左上から順に埋めると読み込み中に見える。順不同にすることで完成が予測できず、最後の1枚まで見ることになる
- ★**未描画セルも同じ順序・同じ重みで置く。** 飛ばしたり最後にまとめたりしない。記録された1日と記録されなかった1日を同格に扱うため

#### 三拍にする理由 ★設計上の核

作品と抽選結果を同時に出すと、視線が結果に持っていかれて作品を見なくなる。**先に作品を見せ切ってから、誰が預かるかを告げる。** 抽選は付随的なものであって主役ではない、という順序を体で覚えさせる。この順序を入れ替えてはならない。

#### 実装上の必須要件

- ★**演出は初回表示時にのみ再生する。** 二度目以降は完成形を即座に表示する。毎回2.8秒待たされるのは苦痛になる
- ★**再生中にタップで即座に完成形へ飛ばせるようにする。** 演出を強制すると、急いでいる日に嫌われる
- `prefers-reduced-motion` が有効な場合は演出を行わず、完成形を表示する

### 6.3 デザイントークン ★v0.6で確定

**方向性**: ホワイトキューブ。白い壁に作品を掛ける現代美術館。装飾を持たず、色は作品だけが持つ。

#### 面（surface）

| トークン | 値 | 用途 |
|---|---|---|
| `--sc-bg` | `#F6F5F3` | 壁。アプリ全体の地。純白を避けることで、作品の白い部分が背景に溶けるのを防ぐ |
| `--sc-surface` | `#FFFFFF` | 台座。カード・シート・モーダル |
| `--sc-sunken` | `#EDEBE8` | 沈み。入力欄・非活性領域 |
| `--sc-fill` | `#14130F` | 主操作の塗り（黒ボタン） |
| `--sc-on-fill` | `#FFFFFF` | 主操作の上の文字 |

#### 文字と線（無彩色のみ）

| トークン | 値 | 用途 |
|---|---|---|
| `--sc-ink` | `#14130F` | 本文 |
| `--sc-ink-2` | `#55524B` | 補助テキスト |
| `--sc-ink-3` | `#8C887F` | 微細・プレースホルダ・キャプション |
| `--sc-line` | `#E2DFD9` | 既定のヘアライン |
| `--sc-line-strong` | `#C9C5BD` | 強調された境界・副操作のボーダー |
| `--sc-danger` | `#A32D2D` | **唯一の有彩色。** 破壊的操作とエラーにのみ使用 |
| `--sc-danger-line` | `#E8CFCF` | 同上のボーダー |

**全ての無彩色はわずかに暖色へ寄せてある。** 純粋なグレーは画面を冷たく事務的にするため、中間色すべてに微量の黄味を含めている。

**アクセント色を持たない。** 操作の階層は黒（`--sc-fill`）と白の対比、線の強弱、余白で表現する。`--sc-danger` を装飾や強調に流用してはならない。

#### 書体

| 用途 | 指定 |
|---|---|
| サンセリフ | `Inter, 'Noto Sans JP', sans-serif` |
| 等幅 | `ui-monospace, 'SFMono-Regular', 'Roboto Mono', monospace` |

- **`font-family` の順序を必ず守ること。** この順であればラテン文字と数字は Inter、日本語は Noto Sans JP から拾われる。逆順にすると全て Noto になる
- **Noto Sans JP は 400 と 500 のみ読み込む。** 700 は使わない（日本語サブセットが重く、初回表示に影響する）
- 等幅は当面OS標準とする。書体の読み込み量を抑えるため。将来 JetBrains Mono 等へ差し替え可能
- **明朝体は使用しない**（v0.6で廃止）

#### タイプスケール

| 役割 | 指定 |
|---|---|
| display | sans 26 / 500 / 1.5 |
| heading | sans 20 / 500 / 1.5 |
| body | sans 15 / 400 / 1.85 |
| label | sans 13 / 400 |
| **壁のラベル** | **mono 12 / 400 / letter-spacing .1em** |
| 数値・日付 | mono 13 / 400 |

**識別性を等幅が担う。** 明朝を廃したため、記録であることは字面で伝える。作品番号（`SCHIILD 128`）、アトリエ番号、日付、人数、座標はすべて等幅にする。美術館の壁に貼られたキャプションと同じ役割であり、画面全体に「台帳」の質感を与える。

#### 角丸と余白

| トークン | 値 | 用途 |
|---|---|---|
| `--sc-radius` | `8px` | ボタン・入力欄・小要素 |
| `--sc-radius-card` | `12px` | カード・シート |
| `--sc-radius-artwork` | **`0`** | **作品を載せるコンテナ** |

**作品部分の角丸は必ず0とする。** シールトは矩形タイルを敷き詰めたピクセルアートであり、角を丸めると四隅のピクセルが欠ける。柔らかい枠の中に硬い作品が置かれるという対比は意図したものである。

余白スケール: `4 / 8 / 12 / 16 / 24 / 32 / 48`（4pxを基数とする）

#### 配色モード

- **ライトモード専用。** ダークモードを実装しない
- OSのダークモード設定を無視し、`color-scheme: light` を明示すること
- 夜間の減光も実装しない。常に同じ白さを保つ
- ホワイトキューブは意図的な identity であり、暗転させると別のアプリになるため

**受け入れる代償**: 就寝前に投稿する使い方は必ず発生する。暗い部屋で白い画面は目に刺さるが、identity を優先してこれを受け入れる。

#### その他

| 項目 | 指針 |
|---|---|
| アイコン | 1px相当のピクセルアイコン |
| モーション | ピクセルが「置かれる」離散的な動き。滑らかにしすぎない |
| 禁じ手 | いいね数の大きな表示、フォロワー数の競争、無限スクロール |

**装飾を持たないことの帰結**: 色も飾りもないため、崩れをごまかす手段がない。**余白とタイポグラフィの精度に対する要求が通常より高い。** 実装時はスケールから外れた値を使わないこと。

### 6.4 語彙ポリシー ★v0.2で新設

> **実際のUI文字列は別冊『Schiild UI文言集 v1.0』にまとめている。** 約200のキーをi18n展開可能な形式で定義しており、本節の方針はそこで具体化されている。文言を追加・変更する際は必ず文言集の§0「書き方の原則」と禁止語リストに従うこと。

**シールトを「資産」ではなく「預かりもの」として言語化する。**

| 使う語 | 使わない語 |
|---|---|
| 預かる / 預かり手 | 所有する / 所有者 / オーナー |
| 次の人へ渡す | 売却する / 出品する |
| 記録 / 作品 | 資産 / コレクション価値 |
| — | 投資 / 利回り / 値上がり / リターン / 希少価値 |

**実装しないもの**: 価格チャート、取引高、保有ランキング、価格の予測・推奨表示。

Phase 2以降は、規約とマーケット画面の両方に「買い手がつく保証はなく、価格は保証されない」と平文で記載する。ブランド毀損の最大の原因は、運営が煽っていなくてもユーザーが勝手に投機を期待して裏切られることであるため、語彙のレベルで先に潰しておく。

**Phase 1で将来の経済圏を告知しないこと。** 「いずれ売買できるようになります」と匂わせると、作品ではなく含み益を目当てにした層が初期コホートに混ざり、継続率の数字が汚染される。Phase 1のD30は以降の全判断の土台になるため、綺麗に測る。

## 10. 法務・コンプライアンス

**一次配布の無償化により、Phase 1〜2の法的リスクは大幅に縮小した。** ただし以下は依然として弁護士レビューが必要である。以下は論点整理であり、法的助言ではない。

### 10.1 一次配布の無償化で解消された論点

| 論点 | 状態 |
|---|---|
| 賭博罪 | **一次では解消。** 応募に金銭を要さず、外れても損失がないため |
| 金商法（集団投資スキーム） | **一次では解消。** 購入行為が存在しないため |
| 資金決済法（前払式支払手段） | **Phase 1では解消。** KUUNを実装しないため |
| 暗号資産交換業 | **Phase 1〜2では解消。** ポイントとして実装するため |

### 10.2 Phase 1でも残る論点

| 論点 | 内容 |
|---|---|
| **削除権** | ★**退会してもシールトの中の区画は残る**（S-17）。「一度確定した作品を描き直さない」という原則の帰結だが、これは個人情報保護法の利用停止・消去請求に対する事実上の例外を主張するものである。**成立するかどうかは投稿時の利用許諾の設計に依存する。実装より先に、S-17の文言が法的に成立するかを確認すること。** 成立しない場合、§4.7の再生成フローを退会時にも適用する（区画をVoidCell化する）設計変更が必要になる |
| **著作権** | シールトはユーザー写真の派生物。生成・展示・アーカイブ・将来の販売まで含む利用許諾を規約で明確化する。全生命シールトの将来販売を見据えた許諾範囲とすること |
| **肖像権・プライバシー** | 他人の写り込み。§4.7の削除・再生成フローが対応策。旧版90日破棄の妥当性を法務確認すること |
| **プロバイダ責任制限法 / 情報流通プラットフォーム対処法** | 削除申出への対応体制と公表義務 |
| **未成年保護** | Phase 1は無課金のため年齢制限は緩められるが、写真投稿SNSとしての保護措置は必要 |
| **GDPR等** | 海外展開時。写真は生体情報を含みうる。UTC固定は国際展開に有利 |

### 10.3 Phase 2着手前に必ず確認すること

- KUUNのポイント設計が資金決済法上の「前払式支払手段」に該当しないか
- 二次流通における収益分配が金商法の規制対象にならないか（「創作への対価」としての構成が成立するか）
- eKYCと犯収法上の取引時確認の要否
- ストア手数料と外部課金導線の適法性・規約適合性

### 10.4 コンテンツモデレーション

1日1枚という制約は投稿量を抑えるが、**生成物に不適切な画像が混入すると作品ごと汚染される**という固有のリスクがある。

- 投稿時に自動審査を通す。判定は生成バッチの前に完了させる
- `moderation_state = 'rejected'` のシールは生成入力から除外し、その領域はVoidCellになる
- 投稿者には理由とともに通知する。**異議申立の導線は置かない**（v0.7で廃止）
- ★**異議申立を持たないため、除外の閾値は「迷ったら通す」方向に振ること。**
  高い確信度のときだけ自動除外し、灰色の判定は含める。
  写り込み等で実害が生じた場合は §4.7 の削除要請という別経路がすでにあり、
  当事者からの申告で事後に外せる。入口で厳しくする必要はない。
  **異議申立のない設計は、入口を緩くして初めて釣り合う**
- ⚠️ **Phase 3以降で再検討すべき事項**: 2025年施行の情報流通プラットフォーム対処法は、
  大規模事業者に削除申出への対応体制を求めている。MVPの規模では対象外だが、
  成長した場合、または欧州展開時（DSAは内部異議手続きを要求する）には
  この方針の再検討が必要になる
- 事後通報時は §4.7 の再生成フローで対応する

### 14-B. シールト生成エンジン（Phase 0・最優先）

```
要件定義書 §4 に基づき、シールト生成エンジンのプロトタイプを
Rust で実装してください。

【目的】
Phase 0の技術検証です。決定性・分割・性能が要件を満たすかを確かめ、
あわせて「ピクセルアートとして読めるか」を目視評価するための
CLIツールを作ります。
★シールトは1枚の絵として成立している必要はありません（§0.4-2）。
  構図の美しさや全体の統一感を作り込もうとしないでください。
  絵である必要はありませんが、ピクセルアートである必要はあります。

【入出力】
入力:
  --atelier-id <UUID>
  --date <YYYY-MM-DD>          UTC基準
  --capacity <int>             2〜10000
  --render-tier <str>          bsp_128 | bsp_256 | bucket（§4.8）
  --input-dir <path>
  --palette <path>
  --frozen-seed <hex>          任意。指定時はシードを再計算しない
  --resolution <int>           既定128。記号性検証のため可変
  --dither <float>             既定0.6。0.0〜1.0
  --posterize <int>            任意。量子化前のポスタライズ段数
  --out <path>

出力:
  schiild.png (1024x1024) / thumbnail.png (256x256)
  region_map.json / metadata.json / used_seed.txt

【アルゴリズム】
§4.2 を厳密に実装してください。特に以下を守ること:

1. シード決定 ★最重要
   --frozen-seed が指定されていればそれを使い、絶対に再計算しないこと。
   未指定時のみ
     seed = SHA256(algorithm_version || atelier_id || date
                   || concat(sorted(image_sha256)))
   を計算する。
   PRNGは ChaCha20（rand_chacha crate）。MT19937 や ThreadRng は使わない。

   ※ この分岐は G-7（部分再生成の安定性）のために必須です。
     シールを1枚除いて再生成したとき、シードを再計算すると
     BSPの分割そのものが変わり、
     「該当領域だけを穴にする」つもりが別の絵になってしまいます。

2. 矩形分割（BSP）
   - resolution x resolution を BSP で capacity 個の矩形へ再帰的二分割
   - 面積上位45%からランダムに1つ選び、長辺方向に分割する
   - 分割位置 = len/2 + (rng()*2-1) * variance * len * 0.34 を整数へ丸める
   - variance は --variance 引数（既定 0.55）
   - 矩形を PRNG でシャッフルして slot_index へ割り当てる
   - 未投稿スロットの矩形は VoidCell として確保
   ★面積は不揃いになる。これは意図した仕様であり、均等化しないこと

3. 各シールの描画
   ★タイルの縦横比に合わせたセンタークロップ（正方形固定ではない）→
   area-average縮小 → Oklab変換 → 32色パレットへ最近傍量子化 →
   Floyd–Steinberg誤差拡散（強度は引数）→ タイル矩形へ合成
   ※ --posterize 指定時は量子化の前段に適用
   ※ --gutter 引数（0〜3px）でタイル間に余白を入れられるようにすること

4. VoidCell
   パレット最暗色 + PRNG由来のノイズ

5. 全体調整
   領域境界に輪郭線を引かない / 当日の平均色相を微弱に乗算 /
   4隅にバージョン署名パターン（4px）

【決定性の要件（最重要）】
- 同じ入力で2回実行し、出力PNGのバイト列が完全一致すること
- --frozen-seed を指定し、入力から1枚だけ除いて再実行したとき、
  除いた領域以外のピクセルが元の出力とバイト単位で一致すること
- 並列化する場合も浮動小数点の演算順序が変わらないこと
- 上記3点を検証するテストを必ず含めること

【レンダリング階層（§4.8）】
capacity に応じて2つのアルゴリズムを切り替えること:
  bsp_128 (2〜200人)   : 矩形分割(BSP) / 128x128 / 8倍拡大
  bsp_256 (201〜800人) : 矩形分割(BSP) / 256x256 / 4倍拡大
  bucket      (801人〜)    : §4.4のバケット割当 / 256x256 / 4倍拡大
★bsp_256 は拡大率が4倍に落ちるためピクセルアートらしさが
  失われる可能性がある。Phase 0で必ず目視評価し、
  成立しないなら200人超を全て bucket にする判断ができるよう、
  3階層を比較できる形で出力すること

【評価用ツール】
- バッチモード: 参加人数 1/3/7/12/50/200/500/2000 × fill_rate 0.25/0.5/0.75/1.0
  を一括生成し、比較用コンタクトシートを出力
- パラメータ探索モード: resolution × dither × posterize を振って
  グリッド状に並べた比較画像を出力
  ★§4.3の副作用（写真モザイクに見えるリスク）を評価するために必須

【パレット】
§4.3 の方針（知覚的に等間隔な汎用32色）に従い、
写真コーパスからOklab空間でk-means（k=32）を実行して構築する
スクリプトも作成してください。無彩色6段は強制的に含めること。
Phase 0では仮のパレットJSONで動作すれば構いません。

【成果物】
- Rustプロジェクト一式 / README / 決定性テスト
- パレット構築スクリプト
```

```
   - SHA256 を計算し保存
   - トランザクション内で schiils と schiil_posts を同時に作成

2. GET /v1/ateliers/{id}/today
   - 生成エンジンと同じBSP分割ロジックでタイル矩形を計算する
   - ★分割ロジックは生成エンジンと必ず同一の結果になること。
     Rust実装をWASM化して共有するか、分割ロジックを
     生成サービスのAPIとして切り出すこと。
     TypeScriptで再実装して結果がずれるのは許容できない。
   - レスポンスに「対象時間の窓」をユーザーのローカル時刻で含めること

3. POST /v1/schiilds/{id}/decline
   - 現在の預かり手のみ実行可能
   - lottery_order の次点者へ即時に繰下げる
     ★順列は生成時に確定済み。ここで引き直さないこと
   - schiild_custody_events に 'declined' と 'promoted' を記録
   - 全員が辞退したら custodian_user_id = NULL（アトリエ共同保管）
   - Phase 1では受取期限を設けない（休眠判定はPhase 2）

4. GET /v1/schiilds/{id}/lottery
   - 認証不要の公開エンドポイント
   - lottery_seed と順列、再計算手順を返す（検証可能性の担保）

5. PATCH /v1/ateliers/{id}/cover
   - 対象シールトの現在の預かり手のみ実行可能
   - 直近に設定した者が反映される。cover_set_by / cover_set_at を更新
   - アトリエ運営者は解除できる

6. WS /v1/ateliers/{id}/live
   - 投稿時に { type: 'schiil_posted', slot_index, user } を配信
   - 未投稿ユーザーを名指しするイベントは配信しないこと

【レスポンスに含めてはいけないもの】
- 他ユーザーの未投稿状態を「催促可能」な形で提示するデータ
- 価格・価値・希少度ランキングに類する情報
- 将来の経済圏に関する示唆

【共通要件】
- 全エンドポイントにレート制限 / OpenAPI自動生成
- 統合テスト（UTC境界の 23:59 と 00:01 の投稿を必ず含めること）
- 構造化ログ（UTC 00:00 バッチの追跡が最重要）
```

```
- 対象シールを含む全シールトを列挙
- 現行版を schiild_revisions へ退避（purge_after = now + 90日）

- 預かり手へ通知
- 別途、purge_after を過ぎた旧版画像を破棄する定期ジョブを実装
  （dispute_open = true の間は破棄しない。行自体は残す）

【成果物】
- ワーカー実装 / 日付指定の手動実行CLI
```

## 付録: 進め方

1. **14-B を実行して Phase 0 を回す。** 生成物が美しくなければ他の全てが無駄になる
2. **並行して法務相談を開始する。** §10.2 の著作権・肖像権と、§4.7 の90日破棄の妥当性
3. **並行してパレットを構築する。** 写真コーパスの収集からk-meansまで
4. Phase 0 の結果が良ければ、14-C → 14-D → 14-E → 14-F の順に Phase 1 を構築
5. **Phase 1 の継続率が基準を満たしてから、初めて 14-G に着手する**

**最も避けるべき失敗**: 経済圏を先に作ってしまうこと。
KUUNも二次流通も、「毎日1枚撮ることが楽しい」が成立していない限り、
何の価値も生まない。Phase 1を完全無課金としたのは、
その判定を汚さずに測るためである。
