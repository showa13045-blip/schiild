# M1 性能改善と残る計測条件

## 今回の変更

- 同一パスの確認・読み込み・SHA-256計算を実行内で共有。各manifest行の期待ハッシュは引き続き照合する。
- 画像をSHAごとにまとめ、最大8ワーカーで前処理する。各画像を1回だけデコードし、必要なタイル形状ごとのサンプルを共有する。同時に保持するデコード済みRGBは最大8画像（約28MB）。画像内の画素計算は逐次のまま。
- 8bit sRGB変換を同じ式で計算した256値の表から取得。Oklabの立方根や加算順は変更しない。
- 1画像内のRGB→Oklab計算を4096エントリの有界キャッシュで再利用。完全なRGBキーを照合し、衝突時は再計算する。近似色・サンプリング・画素の間引きは使わない。
- バケット補間の参照先を固定長配列へ変更。探索順・近傍の順序・平均の加算順は保持する。
- CLIにworkers / index_ms / sample_ms / unique_paths / decode_count / sample_cache_hitsを追加し、時間の内訳と再利用の効き方を確認できるようにする。

`--workers 1..8`で並列数を指定でき、既定は利用可能CPU数（上限8）。上記実測の変更後は8ワーカー。

入力ファイルは実行中に変更しない契約。キャッシュはプロセス内だけで、別実行に持ち越す永続キャッシュはまだない。

## 実測（このPC、release）

| 条件 | 変更前 | 変更後 |
|---|---:|---:|
| 12人、8種類のJPEG再利用 | 約318ms | 約85ms |
| 500人、8種類のJPEG再利用 | 約9974ms | 約623ms |
| 2000人、8種類のJPEG再利用 | 約8212ms | 120.45 / 112.76 / 119.11ms（3回） |
| 2000人、2000枚の異なるJPEG | 約24370ms（今回の逐次処理版） | 約7663ms |

全てCLIの読み込み・前処理・生成・PNG出力・保存を含む。前後比較は同じ入力とパレットを使う。時間は共有PC上の実測で、CPU周波数・OSキャッシュ等を固定した性能保証ではない。変更前の単発値にはビルドとの同時実行による負荷の影響もあり得る。

2000枚の異なるJPEGの内訳:
- ファイル確認とSHA: 約1431ms
- 画像準備等: 約6143ms
- 描画とPNG: 約79ms
- 合計: 約7663ms

異なるJPEGは、8種類の合成画像へ固有のピクセルマーカーを描き、1080×1080 / JPEG品質85で保存したもの。2000種類のSHAと2000回のデコードを確認した。写真コーパスではなく、全画像を処理する負荷確認用である。

8画像再利用ケースだけを使って200ms達成とは扱わない。異なる2000枚では依然として約7.7秒を要する。**M1の全処理200msは引き続き未達。**

## 出力互換性

変更前実行ファイルと、12 / 500 / 2000人の6成果物（PNG2件、region_map、metadata、state、seed）のバイト一致を確認した。乱数・アルゴリズムバージョン・出力規約は変えていない。
異なる2000枚でも逐次版と並列版の6成果物が一致。CLI検証はワーカー4と1、および入力順序の逆転を比較する。
RGB参照式とのビット一致テスト（65536色）と、1080²画像全体のOklab平均の参照計算一致テストを追加。キャッシュヒットした行の不正な期待ハッシュもCLIテストで拒否する。

## 次の設計案（未承認、未実装）

200msを「日次のアトリエ生成ジョブ」の予算として、写真の受け取り時の前処理と分離する。

1. 投稿受付時にJPEGを検証し、SHAとOklab平均を計算して原本にひもづけて保存する。
2. バケット方式の日次ジョブは、検証済みの平均色から生成する。JPEGを2000枚読み直さない。
3. BSP方式は日次シードでタイル形状が決まるため、バケット平均だけでは代用しない。原本・デコード・縮小の別の高速化が必要。
4. 投稿受付の前処理、日次生成、CLI全処理を別々の指標として測定する。全処理200msを達成したとの表記にはしない。

これは計測範囲とデータ受け渡しの設計に関わるため、採用前にユーザーへ確認する。M2の投稿APIや保存基盤は今回実装していない。
